## 1. Страница квартир (каталог и шахматка)

### Где что лежит
- **Маршрут:** `src/app/(pages)/flats/page.tsx`
- **Фильтры:** `FlatsPageFilterContainer` — десктоп и мобильная версия
- **Каталог:** `FlatsPageCatalog` переключает режимы: block, list, checkmate, checkmatePro
- **Синхронизация с URL:** `lib/flatsFilterUrl.ts` — фильтры в `?priceMin=...&project=...` и т.д.

### Как работают фильтры
- **Список/блок:** фильтры применяются **на API** — `GET /api/properties` с параметрами (priceRange, areaRange, roomCount, district, project, tags). Есть пагинация (`page`, `pageSize=24`), «Показать ещё».
- **Шахматка (checkmate/checkmatePro):** в API уходит только **проект (ЖК)**. По выбранному ЖК запрашиваются **все квартиры** (`allStatuses=1`, `light=1`), без пагинации. Остальные фильтры (цена, площадь, комнаты, район) применяются **на клиенте** через `flatMatchesFilters()` — пересчёт «Найдено N» и подсветка недоступных ячеек.

### Критические риски по шахматке
1. **Загрузка всех квартир ЖК**  
   В `getProperties.ts` при отсутствии `page`/`pageSize` используется цикл: запросы по 100 записей со Strapi до 1000 страниц (до 100 000 квартир). Для крупного ЖК это сотни записей в одном ответе и несколько последовательных запросов.
2. **Нет виртуализации**  
   Каждая квартира — отдельный DOM-элемент в сетке. При 200+ квартирах и смене фильтров возможны подвисания.
3. **Двойной запрос метаданных**  
   И фильтр, и каталог могут вызывать `GET /api/properties?metadata=true` при монтировании — лишний запрос.

### Рекомендации
- Для шахматки: либо передавать все фильтры в API и получать уже отфильтрованный список (с лимитом, например 500), либо оставить «все по ЖК», но ввести **жёсткий лимит** (например, 300) и пагинацию/подгрузку по этажам.
- Рассмотреть виртуализацию сетки (по рядам этажей или по видимой области).
- Метаданные фильтров запрашивать один раз (страница или контекст) и передавать в фильтр и каталог.
- Синхронизировать выбранный ЖК в шахматке с `?project=...` при загрузке страницы.

## 2. Детальная страница квартиры

### Маршрут и компонент
- **Маршрут:** `src/app/(pages)/flats/[id]/page.tsx` (id = documentId квартиры)
- **Компонент:** `FlatsDetailPage` + модальное окно оформления `PayModal`

### Запросы данных
- При загрузке выполняются **два последовательных** запроса:
  1. `GET /api/properties/${id}` — полные данные квартиры (план, проект, условия оплаты и т.д.)
  2. `GET /api/properties/${id}/active-deal` — есть ли активная сделка (влияет на кнопки «Оформить» / «Продолжить подписание»)
- При возврате на вкладку (`visibilitychange`) повторно запрашивается active-deal.
- Если в sessionStorage есть `payDealId`, дополнительно вызывается `GET /api/deals/${id}/summary` для проверки возможности «Продолжить подписание».

### Рекомендации
- Объединить в один endpoint: данные квартиры + active-deal (и при необходимости summary по текущей сессии) — меньше круг-трипов и проще обработка ошибок.
- При открытии PayModal с той же страницы не дублировать запрос квартиры — передавать данные из страницы или кэш по id.

## 3. Типы покупки и сценарии

### Типы
- **100% (полная оплата):** `FullPayment` — один платёж, бронь 2ч
- **Рассрочка:** `Installment` — выбор дат платежей, первоначальный взнос, график
- **Отложенный платёж:** `Deffered` — два платежа (первый/последний)
- **Ипотека:** `Hypothec` — только информационный блок (банки, слайдеры), без создания сделки и договора

### Общий сценарий (кроме ипотеки)
1. На детальной странице пользователь выбирает тип оплаты и нажимает «Оформить» (доступно менеджерам/админам).
2. `POST /api/deals/start` (propertyId, paymentMethod) → создаётся сделка, возвращается `dealDocumentId`.
3. Шаг **Оплата:** выбор опций (бронь, условия), «Далее» → `POST /api/deals/${id}/confirm-payment` с графиком и условиями.
4. Шаг **Контакты:** форма клиента, OTP → `POST /api/deals/${id}/attach-customer`.
5. Шаг **Подписание:** генерация ПДБ, отправка на подпись (Doodocs/TrustMe и т.д.).
6. При закрытии модалки без завершения — `POST /api/deals/${id}/release` для снятия брони.

### Рекомендации
- Единая обработка 401/403 (редирект на логин или «Сессия истекла») после `deals/start` и `confirm-payment`.
- Явные состояния загрузки/disabled на кнопках «Оформить» и «Далее», чтобы исключить двойную отправку.
- Ипотека: либо реализовать сценарий (заявка → бэкенд), либо явно обозначить в UI «Информация», без кнопки оформления.

## 4. Личный кабинет

### Структура меню (menuProfile)
- **Профиль** — PersonalInfo  
- **Gala Bonus** — BonusProfile  
- **Мои объекты** — ObjectProfile (сделки клиента)  
- **Сделки** — DealsKanban (только менеджер/админ)  
- **Договора** — AgreementsList (менеджер/админ)  
- **Касса** — CashierPayments (кассир/админ)  
- **Избранное** — LovelyProfile  
- **Сервис** — ServiceProfile  

### Мои объекты (ObjectProfile)
- **API:** `GET /api/profile/my-deals` — до 50 сделок, с графиками платежей. В ответе по каждой сделке только `property.documentId` и `manager.phone`.
- **Проблема N+1:** для каждой сделки фронт делает отдельный `GET /api/properties/${propertyDocumentId}` для картинки, адреса, ЖК и т.д. При 10 сделках — 1 + 10 запросов.
- Пагинации и кнопки «Обновить» нет.

### Канбан сделок (DealsKanban)
- **API:** `GET /api/manager/deals` с фильтрами (search, project, paymentMethod, overdue, excludeCancelled). Лимит **200** сделок (`pagination[pageSize]=200`).
- Автообновление каждые **45 с**.
- Все 200 карточек рендерятся без пагинации и виртуализации.

### Договора (AgreementsList)
- Один запрос `GET /api/manager/agreements` при монтировании, до 500 записей. Кнопки обновления нет.

### Касса (CashierPayments)
- Один запрос `GET /api/cashier/deals` при монтировании (до 300/1000 в разных частях бэкенда). После подтверждения оплаты список перезапрашивается. Пагинации нет.

### Рекомендации
- **ObjectProfile:** убрать N+1 — либо расширить ответ my-deals минимальными полями property (название, адрес, картинка), либо один batch-запрос свойств по списку documentId.
- **DealsKanban:** ввести пагинацию или «Загрузить ещё» на бэкенде и в UI; при росте числа сделок — виртуализация списка колонок/карточек.
- **AgreementsList / CashierPayments:** кнопка «Обновить»; при росте объёма — пагинация или ограничение выборки.

## 5. Корректность и устойчивость

### Ошибки
- Многие `fetch` обрабатывают ошибки и показывают сообщение (DealsKanban, AgreementsList, CashierPayments, PayModal). В части мест (например, загрузка шахматки) при ошибке только очищается список, без явного сообщения пользователю.
- 403 обрабатывается точечно («только для менеджера», «только для кассира»). Глобальной обработки 401 (редирект на логин) не видно.

### Загрузка и пустые состояния
- Списки/блоки квартир, детальная страница, профильные разделы — есть скелетоны или «Загрузка...».
- Пустые состояния: «Нет квартир по выбранному ЖК и фильтрам», «Нет сделок», «В избранном пока ничего нет» и т.д.

### Граничные случаи
- Устаревшая бронь: отдельного сообщения «Бронь истекла» нет; полагаемся на бэкенд и hasActiveDeal.
- Удалённый проект: пустые название/адрес могут отображаться как пустая строка.
- Невалидный id квартиры: вызывается `notFound()`.

### Рекомендации
- Глобальный обработчик 401 (очистка сессии, редирект на вход).
- Везде, где есть загрузка данных, показывать пользователю ошибку и при возможности «Повторить».
- Явная обработка истёкшей брони (сообщение + при необходимости «Забронировать снова»).

## 6. Нагрузка и масштабируемость

| Участок | Текущее поведение | Риск |
|--------|--------------------|------|
| Список/блок квартир | Пагинация по 24, «Показать ещё» | При большом «Показать ещё» — много DOM, без виртуализации |
| Шахматка | Все квартиры ЖК, фильтры на клиенте | Большие ответы, много запросов в цикле, нет лимита и виртуализации |
| Деталь квартиры | 2 запроса подряд (квартира + active-deal) | Лишний круг-трип |
| PayModal | Повторный запрос квартиры по id | Дублирование с детальной страницей |
| Мои объекты | 1 запрос сделок + N запросов свойств | N+1 при нескольких сделках |
| Канбан сделок | До 200 сделок, автообновление 45 с | Рост числа сделок → тяжёлый рендер и трафик |
| Договора / Касса | Один большой список без пагинации | Рост объёма данных |

### Рекомендации по производительности
- Шахматка: лимит на бэкенде (или фильтры на API) + при необходимости виртуализация по этажам/области.
- Список/блок: при большом количестве «догруженных» карточек — виртуализация (например, react-window).
- Деталь квартиры + PayModal: один комбинированный endpoint или передача данных квартиры в модалку без повторного запроса.
- My-deals: в ответ включить минимальные поля property или один batch GET свойств.
- Канбан: пагинация/курсор на API, «Загрузить ещё» или виртуализация.
- Изображения: проверить `remotePatterns` для Strapi, задать `sizes` у `next/image` где возможно; при необходимости — lazy load и плейсхолдеры.

## 8. Приоритетный список задач

### Реализовано (оптимизации без смены логики/интерфейса)

- **Мои объекты (N+1):** запросы свойств выполняются параллельно (`Promise.all`) по списку уникальных `propertyDocumentId`; один раунд запросов вместо N последовательных.
- **Шахматка:** в `getProperties` при загрузке без пагинации добавлен лимит `MAX_CHESSBOARD_FLATS = 500` — цикл прерывается по достижении лимита.
- **401:** в `lib/authApi.ts` при ответе 401 из `apiGet`/`apiPost` выполняется `window.location.assign("/")`.
- **Деталь квартиры:** запросы `GET /api/properties/${id}` и `GET /api/properties/${id}/active-deal` выполняются параллельно (`Promise.all`).
- **PayModal:** при открытии с детальной страницы используется переданный в Redux `flat` (по совпадению `id`); повторный запрос квартиры не выполняется.
- **Договора и Касса:** добавлена кнопка «Обновить» (вызов существующего load/loadAgreements).

### Остаётся на будущее

1. **Средний приоритет**  
   - Пагинация или «Загрузить ещё» для канбана сделок.  
   - Batch-ответ my-deals с полями property (альтернатива параллельным запросам).

2. **Низкий приоритет**  
   - Виртуализация шахматки при большом числе квартир.  
   - Виртуализация списка карточек в списке/блоке при большом «Показать ещё».  
   - Один общий запрос метаданных фильтров для фильтра и каталога.
